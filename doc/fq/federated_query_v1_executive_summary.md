# MatrixOne 联邦查询 V1 管理摘要

## 1. 一句话结论

建议推进 MatrixOne 联邦查询 V1。

V1 的目标不是“把所有异构数据库能力一次做全”，而是先稳定支持：

> **从 MySQL / PostgreSQL / Oracle 读取数据，交给 MatrixOne 做统一查询与计算。**

这是当前客户需求最直接、最有商业价值、同时又能和现有 MO 执行架构自然衔接的做法。

---

## 2. 这件事到底解决什么问题

很多客户的数据不会只放在 MatrixOne 里，还会长期存在 Oracle、MySQL、PostgreSQL 等系统中。

如果 MO 只能查询自己本地的数据，那么客户在做统一分析时，往往只能：

- 先把外部数据搬运进来
- 或者在多个系统里分别执行，再自己拼结果

这两种方式都不理想：

- 数据搬运链路重、时效差、治理成本高
- 多系统分别查询会让统一分析入口缺失

联邦查询 V1 要解决的核心问题就是：

> **让用户可以继续把外部数据库当作数据来源，但把统一查询入口、统一计算能力、统一治理能力放在 MatrixOne。**

---

## 3. 为什么现在值得做

这件事的价值很直接：

- **更容易进客户现网**：客户不需要先完成大规模数据迁移，就能先把 MO 接入分析链路
- **更容易放大 MO 计算价值**：即使数据还在外部，客户也可以先用 MO 做统一查询、JOIN、聚合和后续扩展
- **更容易形成产品闭环**：后续无论是更强 pushdown、缓存、导入加速，还是更深的优化器接入，都有清晰演进路径

从产品切入角度看，这不是“替代导入”，而是：

> **给客户一个更低门槛、更快见效的使用 MO 的入口。**

---

## 4. V1 最终要交付什么

V1 交付的不是一个 demo，而是一套可持续演进的正式能力：

### 4.1 支持的数据源

- MySQL
- PostgreSQL
- Oracle

### 4.2 支持的核心能力

- 在 MO 中配置外部连接
- 在 MO 中注册外部 catalog
- 将远端表以 foreign table 的方式导入到 MO 元数据中
- 直接查询 foreign table
- 支持本地表和 foreign table 做 JOIN
- 支持对 foreign table 做聚合
- 支持 explain、metrics、timeout、cancel、refresh

### 4.3 数据怎么流动

V1 的基本模式是：

- 远端数据库负责提供数据
- MatrixOne 负责统一 SQL 入口、查询规划和本地计算

也就是说，**V1 主要是“远端读数 + MO 计算”**。

这里特别强调：

> foreign table 导入到 MO 的主要是元数据和 schema，不是把远端业务数据整张落到 MO 本地。

---

## 5. 为什么方案定成这样

这次设计最重要的一个判断是：

> **联邦查询必须走 MatrixOne 现有主执行链路，而不是单独搞一套长期并存的旁路执行框架。**

所以 V1 冻结的主路径是：

- `TABLE_SCAN -> Relation -> Reader`

这样做的好处很大：

- **工程上更稳**：复用现有主链路，不额外养一套长期独立扫描框架
- **后续更容易扩展**：优化器、统计信息、执行器能力可以逐步接入
- **产品上更一致**：foreign table 在用户视角里仍然是“表”，而不是另一种完全割裂的对象

对象模型最终定为：

- `CONNECTION`
- `EXTERNAL CATALOG`
- `IMPORTED FOREIGN TABLE`

这个模型的优点是：

- 对用户认知清晰
- 对多数据源扩展友好
- 对未来增强能力预留空间

---

## 6. 为什么 V1 不直接做得更大

这次不是保守，而是有意识地把 **“必须先做对”** 和 **“以后可以继续做大”** 分开。

V1 明确先不做：

- multi-CN foreign scan
- foreign DML / 外部写入
- 跨源事务一致性
- 跨源 join pushdown
- 复杂 agg / 复杂函数 pushdown
- 自动 schema 同步
- direct `catalog.schema.table`

原因很简单：

- 这些能力技术风险更高
- 很多能力会直接改变一致性、执行模型或运维复杂度
- 如果在 V1 一起做，容易把“先把主链路稳定跑通”这件事拖慢

所以 V1 的策略是：

> **先把最核心、最有客户价值、又最容易形成正式产品能力的部分做稳。**

---

## 7. 为什么数据源顺序是 MySQL -> PostgreSQL -> Oracle

这个顺序不是随意排的，而是为了降低整体风险：

### 7.1 先做 MySQL

因为最适合快速跑通第一条真实链路。

### 7.2 再做 PostgreSQL

因为 PostgreSQL 很适合验证这套抽象是不是真的“通用”，特别是：

- catalog / schema 边界
- identifier 规则
- type mapping
- session 参数分层

### 7.3 最后做 Oracle

因为 Oracle 的方言和类型差异更大，适合在前面抽象已经稳定后再纳入。

这个顺序的本质是：

> **先跑通，再验证抽象，再验证高差异企业数据库。**

---

## 8. 对老板最重要的几个收益判断

如果只看管理视角，这个项目最重要的收益有 4 个：

### 8.1 更强的客户切入能力

客户不需要先完成大规模迁移，就可以先把 MO 纳入统一分析体系。

### 8.2 更清晰的产品定位

MO 不只是“自有存储的数据仓引擎”，而是可以逐步成为“统一查询与计算入口”。

### 8.3 更好的后续扩展基础

一旦 V1 的对象模型、执行模型、adapter 机制稳定下来，后续很多增强都可以在此基础上演进，而不需要推倒重来。

### 8.4 更容易形成商业闭环

先解决“能接入、能统一查询、能看见价值”，后续再逐步叠加更深的性能和治理能力。

---

## 9. 风险点与控制方式

这件事不是没有风险，但风险是可控的。

### 9.1 主要风险

- 异构数据库方言差异大
- 类型映射容易出现边界问题
- pushdown 做激进了容易出结果语义问题
- schema drift 会带来运行时不一致

### 9.2 控制方式

- V1 先强制单 CN，降低执行复杂度
- pushdown 采用 capability-based 保守策略，正确性优先于覆盖率
- schema drift 采用“本地 schema 固化 + 显式 refresh”
- 先按 MySQL -> PostgreSQL -> Oracle 的顺序分阶段落地

所以这个项目的风险控制逻辑不是“什么都不做”，而是：

> **先用保守但正式的能力，把正确性和产品结构立住。**

---

## 10. 最终判断

如果用一句管理层更容易决策的话来概括：

> **联邦查询 V1 值得做，而且应该做成正式能力；但首版重点不是“无限扩范围”，而是“先把远端读数 + MO 计算这条主链路做成可靠产品”。**

这套方案的优点是：

- 当前客户价值明确
- 技术路线和 MO 主架构一致
- 后续扩展空间足够大
- 首版风险相对可控

因此，这个 V1 方案适合作为：

> **MatrixOne 联邦查询能力的正式起点。**
