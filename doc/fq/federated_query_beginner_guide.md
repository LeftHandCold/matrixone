# MatrixOne 联邦查询入门说明

## 1. 这份文档是写给谁的

这份文档是写给**刚接触联邦查询、还不太熟悉数据库内部实现**的人看的。

它的目标不是讲代码细节，而是先让你明白：

- 联邦查询到底是什么
- 为什么 MatrixOne 需要它
- 它和“导数据”“同步数据”有什么区别
- 在 MatrixOne 里，它大概会怎么工作
- 你后面应该怎么读 `doc/fq/` 里那些设计文档

如果你先把这篇看懂，再去看后面的设计稿，会轻松很多。

---

## 2. 一句话先讲明白：联邦查询是什么

**联邦查询（Federated Query）**，你可以简单理解成：

> **在 MatrixOne 里写 SQL，但数据不一定都在 MatrixOne 本地，有些数据可以临时去别的数据库里读。**

比如：

- 一部分数据在 MatrixOne
- 一部分数据在 MySQL
- 一部分数据在 PostgreSQL
- 一部分数据在 Oracle

联邦查询的目标，就是让你尽量用统一的 SQL 方式去访问这些数据，而不是每个库都单独连、单独查、再手工拼结果。

---

## 3. 可以把它类比成什么

你可以把 MatrixOne 想成一个“总调度中心”。

平时查本地表，就像：

- 你去自己的仓库取货

联邦查询则像：

- 你在总调度中心下单
- 调度中心发现有些货不在本仓
- 它去别的仓库（MySQL / PG / Oracle）拿一部分
- 拿回来后，再在本地做筛选、关联、汇总
- 最后把结果统一返回给你

这里很关键的一点是：

**你面对的是 MatrixOne，一个统一入口；但真正的数据来源可以是多个地方。**

---

## 4. 它不是什么

很多人第一次听“联邦查询”，容易把它和下面几件事混在一起。

### 4.1 它不是“提前把数据都同步过来”

如果你先把 Oracle 数据全量导入 MatrixOne，再在 MatrixOne 查，这更像：

- 数据迁移
- 数据同步
- ETL

而联邦查询更像：

- **查的时候再去远端读**

当然，实际设计里也可能会有“导入表定义”“缓存元数据”这种动作，但那不是把业务数据整库搬过来。

### 4.2 它不是“跨库写事务”

联邦查询最容易先做好的部分，是：

- **读**

最难的部分，是：

- 跨多个数据库一起写
- 跨多个数据库保证统一事务
- 跨多个数据库保证统一快照

所以你看到设计文档里很多地方强调“先读、后写”，这是因为**读联邦和写联邦不是一个难度级别**。

### 4.3 它不是“什么 SQL 都一定能下推到远端”

联邦查询里有个常见词叫 **pushdown（下推）**。

意思是：

- MatrixOne 发现某些过滤条件、列裁剪、limit，可以安全地交给远端数据库做
- 这样远端先过滤，拉回来的数据更少，性能更好

但不是所有操作都适合下推。

比如：

- 简单过滤，一般比较适合下推
- 复杂 join / agg / 函数，不一定适合

因为不同数据库的语义可能不完全一样。

---

## 5. 为什么 MatrixOne 需要联邦查询

因为很多客户的现实情况不是：

- “所有数据都已经在 MatrixOne 里”

而是：

- 历史系统里已经有 MySQL / PostgreSQL / Oracle
- 新业务想逐步转到 MatrixOne
- 但不想一开始就做大规模迁移

这个时候，联邦查询就很有价值。

它能带来的直接好处有：

1. **降低迁移门槛**
   - 先接入、先能查，再决定哪些数据慢慢迁

2. **统一访问入口**
   - 用户更希望在 MatrixOne 里统一写 SQL，而不是同时维护多个连接和查询口径

3. **方便混合分析**
   - 某些分析需要把 MO 本地数据和外部数据库数据放在一起看

4. **更符合企业实际**
   - 现实世界里，系统往往不是“一步到位全替换”，而是长期混合存在

## 6. 在 MatrixOne 里，大概会有哪几个核心对象

为了让联邦查询可管理、可扩展，文档里把对象分成了三层。你先记住这三个词就行：

1. `CONNECTION`
2. `EXTERNAL CATALOG`
3. `FOREIGN TABLE`

### 6.1 CONNECTION：怎么连远端数据库

你可以把它理解成：

- 地址
- 端口
- 用户名
- 密码
- TLS / timeout 等连接参数

它回答的问题是：

> “我要怎么连上远端数据库？”

### 6.2 EXTERNAL CATALOG：怎么认识远端库里的对象

这个层更像“远端数据库的目录管理器”。

它负责：

- 这个远端库是什么类型（MySQL / PG / Oracle）
- 远端有哪些 schema / table
- 名字怎么映射
- 元数据怎么缓存
- 连接池怎么管

它回答的问题是：

> “我不仅要连上它，还要知道它里面有哪些表、怎么解释这些表。”

### 6.3 FOREIGN TABLE：给 MatrixOne 里的查询一个稳定入口

这层可以理解成：

- 在 MatrixOne 里登记一个“代表远端表”的本地对象

这样后续查询时，MatrixOne 就可以像处理普通表一样处理它，但底层读取来自远端。

这里最容易误解的一点是：

- **登记进 MO 的主要是表定义、映射关系和元数据，不是把远端业务数据整张搬进 MO 本地存储。**

也就是说，联邦查询的核心模式仍然是：

- 查询发生时去远端读数据
- 读回来后交给 MO 计算引擎继续算

它回答的问题是：

> “我怎样在 MatrixOne 里把远端表当成一个稳定、可查询、可管理的对象？”

## 7. 一个简单例子

假设远端 MySQL 里有一张表：

```sql
sales.orders
```

在联邦查询设计里，大概会先做这些事：

### 第一步：创建连接

```sql
CREATE CONNECTION conn_mysql_sales
TYPE = 'mysql'
OPTIONS (...);
```

意思是：

- 告诉 MatrixOne：这是一个可用的 MySQL 连接

### 第二步：创建外部目录

```sql
CREATE EXTERNAL CATALOG mysql_sales
USING CONNECTION conn_mysql_sales
TYPE = 'mysql'
OPTIONS (...);
```

意思是：

- 告诉 MatrixOne：这个连接背后是一套 MySQL catalog，要按 MySQL 规则去发现表、解释元数据

### 第三步：导入远端表

```sql
CREATE FOREIGN TABLE orders_ext
FROM CATALOG mysql_sales.sales.orders;
```

或者：

```sql
IMPORT FOREIGN SCHEMA sales
FROM CATALOG mysql_sales
INTO ext_sales;
```

意思是：

- 把远端表定义引入到 MatrixOne 里，形成可查询的 foreign table
- 这里引入的主要是**定义和映射**，不是把远端业务数据整体落盘到 MO

### 第四步：像查表一样查询

```sql
SELECT order_id, amount
FROM orders_ext
WHERE amount > 100;
```

这时用户看到的体验是：

- 像查 MatrixOne 的表一样查

但系统内部会知道：

- 这张表其实来自远端
- 查询时会去远端拉数据回来，再交给 MO 计算

## 8. 一条联邦查询在系统里大概怎么跑

这是最重要的一部分。你不需要记代码，只要理解流程。

### 8.1 用户写 SQL

比如：

```sql
SELECT * FROM orders_ext WHERE amount > 100;
```

### 8.2 MatrixOne 先像平时一样解析 SQL

也就是说：

- 先做 SQL 解析
- 再做 planner / binder
- 生成查询计划

这一点非常重要。

因为当前设计不是想做一套完全独立的“联邦查询旁路系统”，而是希望：

> **尽量复用 MatrixOne 现有的主查询链路。**

### 8.3 识别出这张表其实是 foreign table

当系统发现：

- `orders_ext` 不是普通本地表
- 它是一个 imported foreign table

那么就不会按普通本地存储去读，而是切到远端读取逻辑。

### 8.4 能下推的操作，尽量交给远端

比如：

- 只查哪些列
- 简单 `WHERE`
- `LIMIT`

如果这些操作能安全翻译成远端 SQL，就先在远端执行。

为什么？

因为这样可以少拉很多数据回来。

### 8.5 拉回来的数据，再进入 MatrixOne 本地执行器

比如：

- 本地 residual filter
- join
- agg
- sort

这也是为什么设计里经常说：

- **join/agg 不一定下推**
- **但 local + foreign JOIN 是可以支持的**

因为一种更稳的做法是：

- 远端负责安全的 scan 和简单过滤
- 更复杂的组合逻辑继续让 MatrixOne 本地算

## 9. 为什么设计里经常强调“走主链路”

你会反复看到一句话：

> 走 `TABLE_SCAN -> Relation -> Reader` 主路径

你不用记住全部术语，先理解它的意思：

- MatrixOne 现在查普通表，本来就有一条成熟的主流程
- 联邦查询最好接到这条成熟流程上
- 而不是另外造一套长期并行的特殊扫描系统

这样做的好处是：

1. **复用现有能力**
   - filter
   - projection
   - join
   - agg
   - explain

2. **系统更统一**
   - 不容易变成“两套扫描体系”

3. **后面演进更自然**
   - 如果功能做大，不用回头推翻第一版

这也是为什么设计里一直不建议长期做一个独立的 `FEDERATED_SCAN` 旁路。

## 10. 为什么文档里会提到“单 CN”“只读”“不做多 CN”

这部分是很多初学者最困惑的地方。

你可能会想：

> “既然要做，就全做啊，为什么还要写这么多先不做？”

原因不是“没必要”，而是**不同问题难度真的不一样**。

### 10.1 只读比可写简单得多

只读联邦主要解决的是：

- 怎么连远端
- 怎么发现远端表
- 怎么把查询拆分成“远端做一部分，本地做一部分”

而可写联邦还要解决：

- 失败回滚
- 提交一致性
- 重试和幂等
- 多源事务边界

这已经不是“顺手再加点功能”的难度了。

### 10.2 单 CN 比多 CN 简单得多

如果只在一个 CN 上跑，很多问题都简单：

- 远端连接在哪建
- reader 生命周期怎么管
- 结果怎么回收

如果是多 CN，就会多出：

- 分布式切分
- 远端 payload 序列化
- 多 reader 协同
- 结果 merge

所以“先单 CN”不是保守，而是为了**先把主链路打通**。

### 10.3 不是什么都应该急着下推

下推越多，性能可能越好。

但同时也意味着：

- 翻译更复杂
- 方言差异更大
- 更容易出现“看起来跑得快，但结果错了”的问题

所以设计里反复强调：

- 先保正确
- 再逐步扩大 pushdown 范围

## 11. 文档里常见术语，给你翻成人话

### `pushdown`

把一部分计算提前交给远端数据库做。

### `catalog-first`

先把“怎么管理远端库”这个控制层建好，再去做具体 foreign table，而不是一张表一张表零散接。

### `imported foreign table`

在 MatrixOne 里登记的、代表远端表的本地对象。

### `schema drift`

远端表结构变了，比如：

- 列增加了
- 列删除了
- 类型变了

### `refresh`

当远端结构变了后，让 MatrixOne 重新刷新认知。

### `ForceOneCN`

强制这类查询先在一个 CN 上跑，避免一开始就进入多 CN 分布式复杂度。

### `dialect adapter`

不同数据库（MySQL / PG / Oracle）的“翻译器”。

因为每种数据库：

- SQL 语法不完全一样
- 类型不完全一样
- 大小写规则不完全一样

所以不能只靠一个通用模板硬套。

---

## 12. 为什么 PostgreSQL 也很重要

你最近也在问 PG 要不要加进来。

这里给你一个直觉：

- MySQL 适合帮我们快速打通第一条链路
- PostgreSQL 适合帮我们验证抽象是不是够通用
- Oracle 适合帮我们验证高差异方言能不能被稳稳接住

所以 PG 的意义不只是“多一个数据库支持”，而是：

> 它能帮我们更早发现 external catalog、schema、identifier、type mapping 这些抽象是不是设计对了。

## 14. 你现在最需要记住的 5 句话

如果前面内容很多，你先记住这 5 句就够了：

1. **联邦查询 = 在 MatrixOne 里查，但数据可以来自外部数据库。**
2. **它不是先把所有数据搬过来，而是查的时候按需要去远端读。**
3. **在 MatrixOne 里，联邦查询的核心对象是 `CONNECTION + EXTERNAL CATALOG + FOREIGN TABLE`。**
4. **设计上最关键的决策是：复用 MatrixOne 现有查询主链路，而不是另造一套长期旁路系统。**
5. **很多“先不做”不是没价值，而是因为写入、多 CN、跨源事务、激进 pushdown 的难度远高于只读联邦。**

如果你把联邦查询理解成：

> **“让 MatrixOne 变成一个统一查询入口，它自己既能查本地数据，也能按规则去别的数据库取数，再把结果统一处理后返回”**

那你已经抓住它最核心的意思了。
