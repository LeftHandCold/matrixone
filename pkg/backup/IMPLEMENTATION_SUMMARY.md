# 备份保护机制实现总结

## 实现概述

根据用户需求，我们成功实现了一个备份保护机制，解决了备份过程中因时间过长导致 GC 删除备份时间点数据的问题。

## 核心设计原则

1. **简化路径保护**: 去掉了复杂的路径保护逻辑，因为备份涉及的所有文件都在 `shared/` 目录下
2. **基于时间戳保护**: 使用时间戳比较来判断是否需要保护，避免逐个文件检查的性能开销
3. **在 GC 入口处检查**: 在 `ExecuteGlobalCheckpointBasedGC` 函数开始时检查，如果 GC 时间戳受保护则跳过整个 GC 过程
4. **避免循环导入**: 通过函数参数传递保护检查逻辑，避免包之间的循环依赖

## 实现的组件

### 1. BackupProtectionManager (`pkg/backup/protection.go`)
- 管理所有活跃的备份保护
- 提供添加、删除、更新和查询保护的功能
- 自动清理过期的保护（基于心跳超时）
- 线程安全的并发访问

### 2. mo_ctl 命令扩展
- **新增命令**: `BACKUP_PROTECTION`
- **支持操作**: `add`, `remove`, `heartbeat`, `list`
- **通信机制**: 通过现有的 mo_ctl 框架与 TN 节点通信

### 3. TN 端处理逻辑 (`pkg/vm/engine/tae/rpc/handle_debug.go`)
- 实现 `HandleBackupProtection` 方法
- 处理备份保护的增删改查操作
- 返回 JSON 格式的响应

### 4. GC 保护检查 (`pkg/vm/engine/tae/db/gc/v3/window.go`)
- 修改 `ExecuteGlobalCheckpointBasedGC` 函数签名，添加保护检查参数
- 在 GC 执行前检查时间戳是否受保护
- 如果受保护则跳过 GC，返回空的删除列表

### 5. 备份集成 (`pkg/backup/backup.go`)
- 在备份开始时自动添加保护
- 实现心跳机制，每 2 分钟更新一次
- 备份完成后自动清理保护

## 关键特性

### 时间戳保护逻辑
```go
// 如果 GC 时间戳 <= 备份时间戳，则跳过 GC
if gcTS.LE(&backupTS) {
    // 跳过 GC
}
```

### 心跳机制
- **间隔**: 2 分钟
- **超时**: 10 分钟（可配置）
- **自动清理**: 超时后自动移除保护

### 性能优化
- 在 GC 入口处进行一次检查，避免逐个文件检查
- 使用内存中的保护列表，查询速度快
- 最小化对现有 GC 逻辑的影响

## 使用方式

### 自动保护（推荐）
```sql
-- 正常执行备份，系统会自动设置保护
BACKUP DATABASE mydb TO S3 OPTION '{"endpoint":"...", "bucket":"mybucket"}';
```

### 手动控制
```sql
-- 添加保护
SELECT mo_ctl('dn','BACKUP_PROTECTION','{"action":"add","backup_id":"backup-123","backup_ts":"2023-12-01 10:00:00.000000"}');

-- 更新心跳
SELECT mo_ctl('dn','BACKUP_PROTECTION','{"action":"heartbeat","backup_id":"backup-123"}');

-- 移除保护
SELECT mo_ctl('dn','BACKUP_PROTECTION','{"action":"remove","backup_id":"backup-123"}');
```

## 故障处理

### 心跳丢失
- 系统会在 10 分钟后自动清理过期保护
- 备份进程异常退出时不会影响系统稳定性

### 保护管理器重启
- TN 重启后保护会丢失，但这是安全的
- 备份进程会检测到连接中断并重试

### GC 保护失效
- 使用保守策略，出错时倾向于跳过 GC 而不是误删数据

## 监控和日志

### 关键日志事件
- `backup-protection-added`: 保护添加成功
- `backup-protection-removed`: 保护移除成功
- `backup-protection-expired`: 保护超时过期
- `GC-Skipped-Due-To-Backup-Protection`: GC 因保护而跳过

### 性能影响
- **内存使用**: 每个保护条目约 200-300 字节
- **GC 性能**: 增加一次时间戳比较，开销极小
- **网络开销**: 心跳消息 < 1KB，每 2 分钟一次

- **简单高效**: 基于时间戳的简单比较，性能开销极小

- **易于维护**: 代码结构清晰，逻辑简单
